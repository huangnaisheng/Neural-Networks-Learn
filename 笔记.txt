（第二讲看完：矩阵乘法、softmax、交叉熵、autograd 版训练）

1. 矩阵乘法的本质：A 的每一行去配 B 的每一列，做点积（逐项相乘再求和），得到一个数。
   (m,n) @ (n,p) → (m,p)。中间的 n 是点积的长度，被 sum 压掉了，所以消失。
   n 两边必须相等，否则报错。
   和 * 区分：* 是逐元素，形状不变；@ 是行配列，内维被吃掉。
   这个点积在 micrograd 里已经写过：act = sum((wi*xi for wi,xi in zip(w,x)), b)。

2. 有了 @，就消掉了 Neuron / Layer 的两层循环：W 的一行 = 一个神经元的权重。
   但层与层之间还是要顺序算（h2 依赖 h1），这个消不掉。
   附带好处：反向传播也批量了。计算图从几万个 Value 节点掉到十几个 tensor 运算节点，
   不用再对巨大的图做拓扑排序，也才能丢给 GPU。

3. GPU 为什么吃矩阵乘法：输出元素之间完全独立，没有依赖，几千个核可以同时开工。
   而且算术强度高——数据读一次能用很多次，不会被内存带宽拖住。
   串行的只剩层数，所以"越深越慢"。
   CPU 几十核擅长有分支、每步都不同的活；跑 Python 循环是浪费 GPU。

4. softmax = .exp() 再除以总和，就这两步。
   exp 的两个作用：把 logits 的负数变成正数（概率不能为负），并放大差距。
   为什么偏偏用 exp：它是 log 的逆运算，和 -log 损失正好对冲，
   log(softmax(x)) = x - log(Σexp(x))，梯度算出来是 softmax - 1，特别干净。
   数值坑（实测）：logits 很大时裸 exp 会变成 inf，inf/inf = nan。
   F.softmax / F.cross_entropy 内部先减最大值，不会溢出。

5. keepdim 的坑在 softmax 这里又来一次：counts.sum(1, keepdim=True) 不能省。
   torch 里 keepdim 和 keepdims 两个名字都认，但标准写法是 keepdim。

6. Karpathy 那句话：无论网络复杂到 Transformer 还是更远，
   唯一改变的只是 forward pass 怎么写。训练循环、链式法则、交叉熵损失，从头到尾不变。
   所以后面学的每个新组件（attention、残差、LayerNorm）都只是新的"混合信息的方式"，
   不是新原理。

7. 【两种训练方法为什么结果一样】统计法 vs 梯度法，本质是同一个模型。
   一句话机理：xenc 是 one-hot，一行 one-hot 去乘 W，结果就是 W 的某一行原封不动地取出来，
   其他行乘 0 被消掉了。
   所以那个"网络"不是一个 27×27 的整体，而是 27 个完全独立的 27 分类问题。
   每个输入字符对应一个问题，各自一个 softmax，各自被数据逼向自己的经验频率。
   梯度只更新被选中的那一行，27 行之间没有任何耦合。

   W 学出来就是 log(计数)。实测（自己的 notebook）：
      N[0] = [   0, 4410, 1306, 1542, 1690, 1531]
      W[0] = [-3.224, 1.988, 0.771, 0.937, 1.028, 0.929]
   log(4410) - log(1306) = 1.217，而 W 的 1.988 - 0.771 = 1.217，一模一样。
   整个 W 就是 log(N) 加每行一个常数，而 softmax 对每行加减常数免疫
   （分子分母同乘一个数），所以那个常数不影响任何结果 → 两者概率完全相同。

   实测损失：统计法 2.4544（cell 21），梯度法 2.4810（cell 50）。
   微小的差来自三处：+0.01*(W**2).mean() 正则把 W 往 0 拽；
   P[0][0]=0 但 softmax 到不了 0（学成 0.0007）；步数不够。

   那为什么还要学梯度这一套：统计法只对 bigram 成立。
   看前两个字符，表就变成 27×27×27，三个就指数爆炸，而且大量组合出现 0 次没法办。
   梯度法能加参数、加层、加非线性，输入还能换成 embedding 让相似字符共享强度。
   关系是：统计法是标准答案，梯度法是通往更复杂模型的路径。

2. C = torch.randn((27, 2)) 里第二维 2 是什么：
   第一维 27 = 有几个字符（数据决定）；第二维 2 = 用几个数字描述一个字符（你定的）。
   emb = C[X] 得到 (32, 3, 2)：32 个样本、3 个上下文位置、每个位置 2 个特征。

3. 为什么不能是纯一维 torch.randn(27)：
   emb 变成 (32, 3)，只剩两维，"样本 / 位置 / 特征"三种含义挤不下，
   后面 torch.unbind(emb, 1) 直接报 IndexError: Dimension out of range。
   (27, 1) 能跑，但拼起来只有 3 个特征，每个字符只有 1 个自由度。

   语义上更重要：一个数只能表达大小关系，等于把 27 个字符强行排在一条直线上。
   可字母本来没有顺序（a<b 只是排序），而 2 维能表达"谁跟谁像"——元音能聚成一团。
   所以 2 只是为了能画图，正式训练用 10。

4. view 是零拷贝，效率极高（实测）：
   只改"怎么读这块内存"（shape/stride），不搬数据。
   torch.cat(torch.unbind(emb,1),1) 和 emb.view(32,6) 结果完全相同（torch.equal = True），
   但 data_ptr 不同：cat 真的新分配内存并复制，view 和原张量是同一块内存。
   所以 Karpathy 说 unbind+cat 是教学用的、慢；view 是实际写法。
   view(-1, 6) 里的 -1 是"这一维你自己算"。

   副作用（坑）：view 和原张量共享内存，改一个另一个跟着变。
       b[0,0] = 999 之后，emb[0,0,0] 也变成 999。

   限制：view 要求内存连续，否则 RuntimeError。
   转置后的张量就不连续（t.T.is_contiguous() 为 False）。
   reshape 是安全版：不连续时会自己复制一份再变形，所以永远能用。

5. F.cross_entropy(logits, Y) 就是你手写的那三行压成一个函数：
   exp → 归一化 → 取答案那格 → log → 取负 → 求平均。
   手写版和内置版实测完全相同（都是 3.5472004413604736），梯度也只差 1.49e-08。

   最重要的坑：喂 logits，不喂 probs。它内部会自己做 softmax，
   传 probs 进去等于 softmax 两次，不报错只是答案错（实测 3.2768 而不是 3.5472）。

   Y 直接给整数下标，不用 one-hot。
   正则项要自己加在外面：F.cross_entropy(logits, ys) + 0.01*(W**2).mean()
   它就是这一句，从 makemore 一直到 GPT 都不变。

   梯度简单得过分：(softmax(logits) - onehot(Y)) / N
   也就是正确答案那格是 p-1，其他格是 p。不用手推链式法则。
   原因还是 exp 和 log 互相抵消，梯度里只剩一次减法。

   另有两点实际好处：内部先减最大值再 exp，所以不会溢出成 nan；
   不会把中间的概率矩阵和它的梯度都留在显存里。

   附：probs[torch.arange(5), ys] 是花式索引，两个数组配对取，
   等于每行只挑出正确答案那格的概率。内置版直接吃 ys 下标，不用自己造。

   三个注意：.to() 写在循环外面（每步搬数据会把加速全抵消）；
   参数设备不一致会报 Expected all tensors to be on the same device；
   generator 也要生成在对应设备上。

   但结论是：这几讲的模型太小，GPU 反而更慢。27×27 的矩阵、batch 32，
   计算量比 GPU 启动一次 kernel 的开销还小。Karpathy 前几讲自己也不用 GPU。
   GPU 要的是"攒够多一起干"——batch 从 32 加到 4096，CPU 时间涨 100 倍，GPU 几乎不涨。
   所以真要上 GPU，必须同时把 batch size 调大。第 5 讲 WaveNet 才开始有用。

2. 调超参数第一步不是改，是先诊断：看 train loss 和 dev loss 的关系。
   train ≈ dev 且都很高  → 欠拟合，方向是"训练更充分 + 容量更大"
   train 远低于 dev        → 过拟合，方向才是加正则
   我当时是 train 2.3934 / dev 2.3992，几乎一样，所以是欠拟合。
   证据：加 weight decay 后 dev 反而变差（2.2218 vs 2.2129）。正则用在欠拟合上就是帮倒忙。

3. 实测结果（同一份数据划分，random.seed(42)）：
   配置                              train     dev
   原始 (lr=0.01, 50k, batch32)      2.3934   2.3992
   只把 lr 改成 0.1                   2.3112   2.3385
   lr 三阶段衰减 + 100k 步             2.1794   2.2129   ← 单项收益最大
   batch=64 + lr=0.2                  2.1208   2.1563   ← 最好
   d=24, hidden=300                   2.0868   2.2035   ← train 掉很多，dev 没怎么动，过拟合苗头
   block_size=4                       2.2289   2.2443   ← 更差，没用
   + weight decay 0.01                2.1989   2.2218   ← 更差
   Adam lr=1e-3, 150k                 2.1097   2.1738   ← 不如调好 lr 的 SGD

   结论排序：
   (1) 学习率 + 衰减，收益最大。0.01 对这个模型太小了。
   (2) batch size 和学习率要一起改，小 batch 不敢用大 lr。batch 32 → 64，lr 上限提到 0.2。
   (3) 加宽（d、hidden）会让 train 猛降但 dev 只微动，说明开始过拟合。
   (4) block_size 3 → 4 实测没用，而且 W1 形状和 emb.view(-1,30) 都要跟着改，容易错。
   (5) Adam 对学习率不敏感，省事，但最终精度不如调好的 SGD。

4. 最终成绩：batch 64，lr = 0.1 if i < 100000 else 0.01
   → dev 2.1589，train 2.119，差距只有 0.04。
   这基本就是这套架构的天花板了，再调参是边际收益。

   dev 是拿来调参的，会被"污染"，偏乐观。
   test 是没动过的，看完那一个数才是诚实成绩，而且只能看一次，看完不能拿它继续调。

（第四讲看到 41 分：激活值、梯度、初始化）

1. tanh 饱和就是梯度消失的根源。tanh 的导数是 1 - tanh(x)^2：
      x        0.0     1.0      2.0      3.0      5.0
      tanh     0.0   0.7616   0.964   0.9951   0.9999
      导数     1.0   0.4200   0.0707   0.00987  0.000182
   在 x=5 处导数只有 0.00018，梯度每经过一层就被乘掉这么多，
   几层连乘就是指数级衰减。tanh 的导数最大只有 1（在 x=0），所以天生只会缩不会放大。

   用我自己的初始化实测：hpreact 的 std = 5.69，|tanh| > 0.99 的单元占 63.5%，
   也就是 200 个神经元里一上来就有 127 个饱和。这就是"起点错了"。

2. "死神经元"的准确含义，两个容易混的地方：
   (a) 梯度太小 = 神经元学不动（死）；梯度太大 = 整锅爆炸（loss 变 NaN）。
       这是两种完全不同的失败，处理方式也不同。
   (b) tanh 饱和是"休眠"，可逆；ReLU 是"死亡"，不可逆。
       tanh: x=5 时 grad=0.00018，但 x=0.5 时 grad=0.78 —— 输入变小，梯度就回来了。
       ReLU: x<0 时 grad 恒为 0，权重不更新 → 输入还是负 → 永远出不来。

   死神经元不代表模型坏了：网络是过参数化的，200 个里死一半通常还剩够用，
   loss 不会明显变差。代价体现在别处：有效容量下降、算力浪费、换个种子结果波动大。

3. Karpathy 的三步修复（他自己的 loss 记录）：
   原始                              train 2.1245  val 2.1682
   修 softmax confidently wrong      train 2.07    val 2.13
   修 tanh 层初始过饱和               train 2.0356  val 2.1027

   两处修的完全是不同的东西：
   - "confidently wrong" 修的是输出层 W2 和 b2（乘 0.01 / 乘 0）
   - tanh 过饱和修的是 W1 和 b1
   都只是把初始化的随机数乘个系数，一步额外算力都没花。

4. "confidently wrong" 到底什么意思：loss 只看正确答案那一格的概率，
   完全不管模型最自信的是哪一类。实测同一个样本：
      原始:  logits 范围 [-25.6, 26.0]，最自信的类拿 0.9998，
             正确答案只拿到 0.00000000001，loss = 51.64
             原因：logit 差 51.63，概率比就是 e^-51.63
      修后:  logits 范围 [-0.3, 0.3]，所有类都在 1/27 附近，loss = 3.55
   谦虚地错是免费的（每类留 1/27，loss 就是 log(27)=3.296）；
   傲慢地错要付指数级代价。所以模型不是从零开始，是从负数开始。

   为什么 W2 要乘 0.01：logits 里每个数是 200 项相加，方差相加 → 标准差乘 √200 ≈ 14。
   b2 必须一起清零，因为 b2 是直接加在字符分数上的（std 0.85），
   W2 缩到 0.01 后 logits 只有 0.14，b2 的 0.85 反而变成主导，模型又会固执地偏爱某几个字符。

5. 四个参数各自干什么（这次才真正搞清楚）：
   C  (27,10)  字典：每个字符一个 10 维"画像"
   W1 (30,200) 特征工厂：每一列是一个特征检测器，"我关心的那个特征在输入里有多强"
   b1 (200)    门槛：每个检测器的基础倾向，不看输入也能给分
   W2 (200,27) 投票：每一列对应一个输出字符，"200 个特征我各看多重"
   b2 (27)     先验偏好：哪些字符本来就常见

   一句话记法：W 管"怎么组合输入"，b 管"不看输入时起点在哪"。

6. 尺度会被放大 √(fan_in) 倍，这是所有初始化问题的数学根源：
   30 项相加  → std 乘 √30 ≈ 5.48（实测 5.42）
   200 项相加 → std 乘 √200 ≈ 14.14（实测 14.16）

   Kaiming init 就是按这个推的：缩放系数 = gain / √fan_in
   所以 W1 那一行 = torch.randn((n_embd*block_size, n_hidden)) * (5/3) / (n_embd*block_size)**0.5
   实际系数 (5/3)/√30 = 0.3043，和他之前手调的 0.2 差不多。

   两个因子各自的分工：
   / √30    抵消 30 项相加的放大（数学必然，非做不可，不做饱和率 62.5%）
   * 5/3    补偿 tanh 的压缩（tanh 会把信号压扁，tanh 输出 std 从 1 掉到 0.63）
   5/3 叫 gain（增益），不同激活函数不一样：ReLU 是 √2，tanh 是 5/3，线性是 1。
   PyTorch 已封装：torch.nn.init.kaiming_normal_(W, nonlinearity='tanh')

   注意 5/3 是取舍不是纯赚：实测 pre_std 1.68、tanh 输出 std 0.76（信号更强），
   但饱和率从 1.1% 回升到 11.5%。Karpathy 叫它 semi-principled 就是因为
   它是论文推荐的通用值，不是为你这个网络推出来的最优值。

   装上 BatchNorm 之后这些手算系数全都不需要了。

（第四讲看到 1 小时 20 分：BatchNorm、滑动统计量）

1. BatchNorm 那行代码 = 两件事拼起来：
      hpreact = bngain * (hpreact - bnmeani) / bnstdi + bnbias
                ① 归一化：(x - 均值) / 标准差，就是普通的 z-score
                ② 仿射：* gain + bias，把"偏离规范"的自由度还给网络

   先纠正一个说法：它不是让数据变成高斯分布，只是让均值 0、标准差 1。
   分布形状完全不变（实测偏度 0.006 → 0.002，高斯应该是 0）。

2. bnmeani / bnstdi 是怎么算的：hpreact.mean(0, keepdim=True)，
   沿第 0 维（batch）求平均，得到 200 个数——每个隐藏单元一个。
   也就是"对每个神经元，看它在整个 batch 里输出的分布，拿这个分布去归一化它自己"。
   每个神经元各算各的。

3. 为什么这比 Kaiming init 强：实测换四种初始化尺度，BN 之后全是 std 1
      W1 尺度 0.05 → BN 前 std 0.28  → BN 后 1.00
      W1 尺度 0.5  → BN 前 std 2.76  → BN 后 1.00
      W1 尺度 1.0  → BN 前 std 5.58  → BN 后 1.00
      W1 尺度 5.0  → BN 前 std 27.59 → BN 后 1.00
   Kaiming 是"猜一个系数去抵消放大"，猜错了就饱和；
   BN 是"直接量出当前这批数据的实际标准差再除"，精确，不靠猜。
   而且不止初始化，训练到第 10000 步也照样是 std 1。

4. 顺手解释 b1 为什么能删掉：BN 里有"减均值"这一步，加常数再减均值，
   常数直接被抹掉。实测加一个 std=10 的 b1，BN 输出最大差别 0.0000026（浮点误差）。
   通用道理：紧跟在归一化层前面的偏置项是多余的。

5. bngain / bnbias 初始值是 1 和 0（ones / zeros），所以训练第一步等于纯归一化，
   之后梯度下降自己去调。归一化保稳定，gain/bias 保表达力，两个都可学习。

6. 训练和推理不一样（必须记住）：
   训练时用当前 batch 的真实均值和标准差；
   推理时必须用训练中累积的滑动平均，因为推理可能一次只喂 1 个样本，batch 统计量没意义。
   累积方式：bnmean_running = 0.999 * bnmean_running + 0.001 * bnmeani
   （bnstd 同理）。这也是为什么 batch 太小的时候 BN 效果差——统计量本身不稳。

1. 那个 layers 列表里的两处代码：
   layers[-1] 是负数索引，就是最后一个。它是 BatchNorm1d(vocab_size)，作用在 logits 上，
   所以改的是它的 gamma（乘 0.1），让初始 logits 变小 -> softmax 接近均匀 -> 避免 confidently wrong。
   为什么改 gamma 而不是 weight：前面有 BN，改 weight 的尺度会被 BN 完全抹平，
   只有 gamma 活在归一化之后，是唯一还能影响尺度的地方。
   （注释掉的那行 #layers[-1].weight *= 0.1 是没 BN 的旧版本留下的，现在 last 是 BN，
    它根本没有 weight 属性，去掉注释会 AttributeError。）

   for layer in layers[:-1]: 是"除最后一个以外全部"，isinstance(layer, Linear) 是必须的，
   因为 BatchNorm1d 和 Tanh 都没有 weight 属性，不检查就会 AttributeError。
   里面那句 layer.weight *= 1.0 是空操作——这是 Karpathy 故意留的演示：
   有了 BN，初始化的 gain 已经不重要了（实测乘 1.0 和乘 5/3，BN 输出完全相同）。
   所有 Linear 都写 bias=False，因为紧跟的 BN 会减均值，偏置被抹掉。

2. 类定义 ≠ 创建对象（这次终于搞清楚）：
   class BatchNorm1d: 只是写了一份配方，一行都不执行。
   对象是在执行 layers = [...] 时、遇到 BatchNorm1d(n_hidden) 的那一瞬间诞生的，同时跑一次 __init__。
   我这套 layers 里有 6 个 BatchNorm1d（5 个 n_hidden=100，1 个 vocab_size=27），各自独立。
   实测改 layers[0].gamma[0] 不影响 layers[1]。

   __init__ 创建时跑 1 次；__call__ 只有写 bn(x) 时才跑，训练循环里每步 1 次。
   创建时 __call__ 一次都不会跑。

   self 就是"当前这个对象"。parameters() 返回的是 [self.gamma, self.beta] 本身（引用不是拷贝），
   所以后面 p.requires_grad = True 改的就是对象内部的张量。写成 clone() 整条训练链就断了。

3. 为什么加了 tanh 才算真正的神经网络（差距为什么这么大）：
   没有非线性时，W1 @ W2 @ W3 可以合并成一个矩阵（实测三层 == 一层，True）。
   叠 100 层 100x100 线性层，数学上等价于一个 100x100 矩阵，99 万参数全是白算的。
   线性层只能旋转/拉伸/剪切空间，直线永远是直线。

   实测拟合 y = x^2：
      纯线性模型       MSE = 1.2601
      线性+tanh+线性   MSE = 0.0057     ← 降 220 倍
      （y 本身的方差 = 1.2850，也就是"永远输出平均值"的水平）
   也就是说纯线性模型几乎什么都没学到。

   tanh 是逐元素的弯曲，插进去之后矩阵就没法合并了（实测 False）。
   一层"线性+BN+tanh" = 折一次空间；层数 = 折的次数。折够多，任何形状的边界都能围出来。

   更深一层的意义：第 1 层的 100 个神经元是 100 个特征检测器，第 2 层看的是它们的回答，
   在组合特征。没有人告诉它找什么，是任务逼它自己发明概念。纯线性层合并之后中间不存在
   任何可被下一层引用的新概念，所以做不到。

   历史：1969 Minsky & Papert 证明单层感知机做不了 XOR，导致第一次 AI 寒冬。

   三明治分工：Linear 混合信息、BN 管尺度、tanh 弯曲。缺一不可。
   （只有 tanh 没有 Linear，就是 100 个互不交流的一维问题。）

4. 激活分布直方图怎么看（这是诊断工具，比只看 loss 有用）：
   一条曲线 = 一个 Tanh 层的输出分布，5 层应该有 5 条叠在一起。

   健康：钟形、中心在 0、std 0.5~0.7、5 条曲线宽度接近、互相重叠
   饱和：曲线在 ±1 处堆出尖峰（神经元死了）
   塌陷：曲线逐层变窄、挤成 0 附近一根竖线（也是死，另一种死法）

   实测三种情况（同样的网络结构）：
      有 BN             五层 std 全是 0.62~0.64，饱和率 3%   —— 理想
      无 BN 原始 randn   std 0.623 -> 0.483 -> 0.416 -> 0.361 -> 0.333  逐层萎缩
      无 BN gain=0.2     std 0.191 -> 0.038 -> 0.008 -> 0.002 -> 0.000  灾难性塌陷

1. 第一讲的拓扑排序（我答错在措辞）：
   `build_topo` 的 post-order append 出来【已经】是一个合法拓扑序（子在前、父在后）。
   `reversed()` 不是为了"变成拓扑序"，而是换方向——反向传播必须"消费者先处理，
   生产者后处理"，因为一个节点要等所有下游把梯度贡献上来，它的 grad 才是最终值。
   两个都是拓扑序，一个顺流一个逆流。

   前序 bug 的症状也不是"梯度变成 0"，而是【梯度不完整】：
   直连输出节点的边通常还是对的，凡是经过中间节点的路径全丢。
   实测 e = a*b + a（a=1,b=2）：a.grad 得 1（应为 3），b.grad 得 0（应为 1）。
   c = a^3（a=3）：得 9（应为 27）。都不是 0。

2. 为什么梯度必须 += 而不能 =：一个节点被多处使用时，会收到多份梯度，必须累加。
   真实网络里到处都是这种结构——残差连接 x + f(x)、同一个词向量在句子里出现多次、
   attention 里 Q/K/V 都从同一个输入来。写成 = 只保留最后一份，而且不报错，只是学得慢。
   （PyTorch 里必须手动 p.grad = None 清零，也是同一个累加机制。）

3. keepdim 那题我说漏了最关键一步：不是"少了一个维度"，而是【变成了一行】。
   (27,) 广播时左边补 1 → (1,27)，于是"第 j 列除以第 j 行的和"，方向转了 90 度。
   为什么不报错：27 和 27 对得上。如果矩阵是 (27,10) 就会立刻
   RuntimeError: The size of tensor a (27) must match the size of tensor b (10)。
   方阵掩盖了这个 bug。

4. 统计法 == 梯度法那条链，我当时只记住了第一步。完整的是六步：
   ① one-hot @ W 取出 W 的某一行（27 行互不影响）
   ② 所以是 27 个独立问题
   ③ 每行经 softmax 是一个 27 分类分布

   过饱和是 tanh 的专门说法（贴到 ±1）。发散 = loss 冲上去甚至变 NaN。

7. 推理为什么不能用 batch 统计量——不是"效果差"，是逻辑上不成立：

   网络彻底失去依赖输入的能力，所有输入给同一个答案。

1. dh = dlogits @ W2.T 是怎么来的：只看一个格子。
   前向 logits[i][j] = Σ_k h[i][k] * W2[k][j]
   所以 ∂logits[i][j]/∂h[i][k] = W2[k][j]
   而 h[i][k] 这一个数影响了全部 27 个输出，要收 27 份梯度：
   dh[i][k] = Σ_j dlogits[i][j] * W2[k][j]
            = dlogits 第 i 行 和 W2 第 k 行的内积
            = (dlogits @ W2.T)[i][k]
   实测：三层 for 循环手算 和 dlogits @ W2.T 完全一致。

2. 矩阵乘反向三件套（前向 C = A @ B）：
   dA = dC @ B.T      dB = A.T @ dC      db = dC.sum(0)
   记法：算谁的梯度，就把另一个操作数转置后挪到对面，dC 留在自己这一侧。
   记住不就有形状兜底——算出来必须和 A、B 同形。
   不转置的话报错很直白：mat1 and mat2 shapes cannot be multiplied (3x5 and 4x5)。

3. 这和"一个数被用几次就收几份"是同一条规则。matmul 只是批量版的复用求和。
   db2 = dlogits.sum(0) 又是一次广播反向求和（消掉的是样本维，所以 sum(0)，
   和 dcounts_sum_inv 那次 sum(1) 方向相反）。

4. 贝塞尔校正：bnvar = 1/(n-1) * (bndiff2).sum(0, keepdim=True)。
   有偏 ÷n / 无偏 ÷(n-1)，差一个 n/(n-1)。
   实测从 N(0,1) 抽 20 万批（真方差 1.0）：
     n=2 时 ÷n 只有 0.4988，÷(n-1) 是 0.9976；
     n=32 时 ÷n 是 0.96875，÷(n-1) 是 1.00000。
   偏小不是随机误差，是系统性偏小。
   原因：减的是 x̄ 不是真值 μ，x̄ 是离这批数据最近的点，
   所以 Σ(x-x̄)² 必然比 Σ(x-μ)² 小。而 Σ(x-x̄) 恒等于 0，
   n 个偏差被锁死一个，自由度只有 n-1，所以除以 n-1。
   实际影响：n=32 时 std 只差 1.6%，n=2 时差 41%。

5. ★ 今天最大的发现：PyTorch 的 BatchNorm 两处用不同的除法。
   归一化这批数据 → 有偏 ÷n
   更新 running_var → 无偏 ÷(n-1)
   实测：bn.running_var == x.var(0, unbiased=True)  True
         归一化输出 == 用 unbiased=False 算的        True
   原因：归一化只管当下这一批，不多不少不必估计；
        running_var 要留给未来所有 batch 用，那是在估计总体方差，必须无偏。
   所以 Karpathy 手写 BN 时用 n-1，是为了和 running_var 对齐。
   （这条也顺带推进了 11-08 待补的 B 项：BN 统计量的语义。）

1. ★ 交叉熵的导数（这条要能自己重新推出来，别的都可以忘）

   起点：
     p_i  = e^{l_i} / Σ_j e^{l_j}
     loss = -log(p_y)

   ① 拆分式（不需要微积分，只用对数律）
      log(a/b) = log a - log b，且 log(e^x) = x
      loss = -[ log(e^{l_y}) - log(S) ]
           = -l_y + log(S)          其中 S = Σ_j e^{l_j}
      分式没了，只剩两项。

   ② 两项分别求导（只用 log→1/x、e^x→e^x、链式法则）
      第一项 -l_y：i==y 时导数 -1，否则 0（l_i 根本不在里面）
      第二项 log(S)：链式法则 = (1/S)·dS/dl_i
        S = e^{l_0} + e^{l_1} + ...，只有含 l_i 的那项不是常数
        dS/dl_i = e^{l_i}
        所以 d/dl_i log(S) = e^{l_i}/S

   ③ 认出来：e^{l_i}/S 按定义就是 softmax 的 p_i
      两项相加：dloss/dl_i = p_i - 1{i==y} = softmax - onehot
      F.cross_entropy 默认对 batch 求均值，所以 dlogits = (softmax - onehot)/n

   对应代码就三行：
     dlogits = F.softmax(logits, 1)
     dlogits[range(n), Yb] -= 1
     dlogits /= n

   为什么结果这么干净，不是巧合：softmax 的定义里自带"除以 S"，log 把除法
   变减法，e^x 的导数又是自己，S 正好被约掉。所以这两个操作天生配对。

2. cmp 表的三列怎么读：
   exact = dt == t.grad（逐位相等），approximate = allclose，maxdiff = 差多少。
   emb 和 C 只有 approximate 而没有 exact，不是算错，是浮点累加顺序不同。
   实测：6 个索引全是 3 时，正序累加和逆序累加差 6.66e-16。
   习惯：手写反向永远用 allclose 判，不用 ==；真正该看的是 maxdiff
   （1e-16 是噪声，1e-3 才是公式错了）。

3. BN 的反向：推过一遍就够了，以后不再手推（实际也没人手推，框架里用的是
   化简后的一行）。只留两个结论：
   ① 那串长公式的长度来自【代数整理】，不来自【求导】。
      梯度本身是三条路加起来（走 x̂、走 μ、走 σ²），这一步不难；
      难的是最后要把 (x-μ) 换成 x̂/inv，再提出公因子 γ·inv/N。
      那是工程整理——为了让结果落在前向已经算过的 bnraw 上，不是数学需要。
      记住这个区分就够了：以后看到长得吓人的公式，先问"这是求导难还是整理难"。
   ② 每个梯度都在 batch 维上做 sum(0)，所以一个样本的梯度会被同批次所有样本
      影响，样本之间强耦合。这也解释了 batch=1 时 BN 为什么两头都塌：
      前向看是 x - x̄ = 0，反向看是 sum(0) 只汇总了一个样本。

1. optimizer = torch.optim.AdamW(m.parameters(), lr=1e-03) 拆两半读：

   所以 lr=1e-3 这种默认值就能跑，不用像 SGD 那样为每一层试。
   顺序上要先 m.to(device) 再建 optimizer —— optimizer 抓的是张量对象本身。

   整个 notebook / 脚本只有三处需要写 device：模型 .to(device)、get_batch 里的 .to(device)、
   generate 里的 torch.zeros(..., device=device)（torch.zeros 不管在哪都默认造 CPU 张量）。

   顺带：loss.item() 会强制同步，循环里别每一步都打。

6. ★ loss 阶梯（自己算的理论值 + 自己跑出来的实测值）：
     随机初始化 logits ~ N(0,1)          4.70     step 0     train 4.73  val 4.72
     只学字母频率、完全不看上下文        3.31     step 300   train 2.81  val 2.82
     看前一个字符（bigram 的理论下限）   2.45     step 900   train 2.49  val 2.51
     真正的语言模型                      ~1.50    step 2700  train 2.47  val 2.49
   900 步就到 2.49，后面 2000 步只赚了 0.03 —— bigram 确实到顶了，继续训是浪费。

7. ★★ 单批 loss 不能用来判断模型好坏，今天被自己骗了一次。
   我先读到 2.39，还以为是超常发挥；其实那是一个 batch（32×8=256 个 token）的瞬时读数。
   按 bigram 的精确概率算 2000 个 batch：均值 2.4502，标准差 0.0707，范围 2.229 ~ 2.732。
   同一个模型、同一份训练集，单批读数能从 2.23 跳到 2.73。2.39 只是均值 -0.9σ，纯噪声。
   接上 estimate_loss（200 批平均）之后，真实值才露出来：train 2.4738 / val 2.4911。
   教训：单批数字什么也说明不了，要么多批平均，要么用固定验证集。

8. bigram 为什么到 2.45 就停死：nn.Embedding(65, 65) 等价于一张
   "上一个字符 -> 下一个字符"的转移概率表，4225 个数，能用的信息只有一个字符。
   它实际学到了：q->u 0.898、句号->换行 0.834、空格->t 0.141、h->e 0.353。
   所以采样出来像英文（字母频率、th/ing/er 这些组合都对），
   但 Wawice、Heriliovets、ndill 都不是词，HAPet / HDERarom 里大写也乱入 ——
   因为生成每个字符时它只知道紧挨着的那一个。这条路到头了。

9. ★ 一个之前没注意的坑：现在的 block_size=8 对 bigram 完全没用。
   (B,8,65) 拉平成 (256,65) 去算 loss，8 个位置是 8 个独立样本，不是 8 个字符的上下文。
   所以把 block_size 调大，bigram 的 loss 一点都不会降。
   这正是下一节的转折点：怎么让模型真的"看到前面好几个字符"。
   路线：先把前几个 embedding 求和/平均（~2.2）-> 再把"平均"换成可训练的权重
   （点积 + softmax = self-attention）-> 最后堆到 6 层 384 维（~1.48）。

1. torch.allclose 的坑（花了最久才想通）。它判的是 |a-b| <= atol + rtol*|b|，默认 atol=1e-8, rtol=1e-5。
   助手实测（seed 和我的 cell 完全一样，可复现）：64 个元素里只有 1 个超，
   diff 3.24e-08，允许 3.02e-08，差 0.2e-8。
   根因：float32 的 eps 是 1.19e-07，根本给不了 1e-8 的绝对精度。
   而且规律很清楚：权重是 1/1、1/2、1/4 的行误差正好 0，1/3、1/5、1/7 一定带舍入；
   再叠加 mean（先加后除）和 BLAS matmul（FMA、累加顺序不同）两条路。
   结论：以后统一用 torch.allclose(a, b, atol=1e-6)，或者直接看 (a-b).abs().max()。

2. 三层结构改造：把 nn.Embedding(65, 65) 拆成
   token_embedding(65,32) + position_embedding(8,32) + lm_head(Linear 32->65)。
   参数 4225 -> 4481。重点不是参数，是"字符的身份"和"预测结果"分开了：
   原来那张表兼着干两件事，输出直接就是 logits，中间没有可以修改的东西。
   现在有了 x (B,T,32) 这条"残差流"——后面 attention 和 MLP 都从它读、往它写。

3. ★ 但这一版还是 bigram。助手用对照脚本训了 4000 步（lr=1e-2）：train 2.4873 / val 2.5164，
   和纯 bigram 的 2.47 / 2.49 一样。
   扰动实验（助手跑的，我自己还没动手）：把 idx[0,0] 改掉一个字符，
   32 个位置的 logits 只有 1 个变了（1.83），其余 31 个 bit 完全相同
   —— forward 里没有任何一步让不同的 t 交互。
   加上一个 attention head 之后，同样只改一个字符，变成 8 个位置都变（整条 b=0）：
     1.01 0.168 0.66 0.619 0.127 0.382 0.0963 0.097
   b=1..3 仍然是全 0（不同序列之间不串）。信息真的开始流动了。
   这就是为什么要写注意力：不是网络不够大，是信息根本没流过。

4. 两个形状细节：
   pos_emb 是 (T,32)，没有 batch 维，靠广播加到 (B,T,32) —— 位置对 4 条序列是同一件事。
   torch.arange(T, device=device) 的 device 不能忘（和 torch.zeros 一样默认 CPU）；
   T > block_size 会 IndexError，因为位置表只有 block_size 行。

5. nn.Linear(n_embd, head_size, bias=False) 就是加权求和：W 的每一行是一套权重，算出一个输出数。
   它和昨天的 wei @ x 是同一个操作，只是换了轴：
     wei 在"时间"维上加权（8 个位置 -> 8 个位置）
     W   在"特征"维上加权（32 个特征 -> 16 个特征）
   权重存成 (out, in) 即 (16,32)，不是 (32,16)；只改最后一维，前面维度原样保留，
   所以能直接吃 (B,T,C)。第 4 节自己写的 Linear 是 (in,out) + x@W，数学一样，只是存反了。

6. Head 类：key / query / value 是三个结构相同、参数不同的 Linear，都做 (B,T,32) -> (B,T,16)。
   q @ k.T -> (B,T,T) 打分表；tril 遮住未来；softmax 归一；wei @ v 混合。
   register_buffer('tril', ...) 用 buffer 而不是普通属性，是为了跟着 .to(device) 走，
   又不会被算进 parameters()。

7. ★ bug：generate 里 idx_cond 裁好了却没用，写的是 self(idx)。
   训练全程正常，只在生成第 9 个字符时炸（idx 长度超过 block_size，位置表越界）。
   报错是 CUDA 的 Assertion `srcIndex < srcSelectDimSize` failed，不是 Python 的 IndexError
   —— GPU 上的越界检查走 C++ 断言。同样代码在 CPU 上跑会直接说
   IndexError: index out of range in self。教训：训练能跑完 ≠ 代码没问题。

8. ★ 隐患：C**-0.5 应该是 head_size**-0.5。
   现在 Head(n_embd) 让 head_size == n_embd == 32，两者数值一样，所以没暴露。
   等做 multi-head，head_size = 32//4 = 8 而 C 还是 32，就差了 2 倍 —— 不报错，只是效果偏。
   这类"现在恰好对"的 bug 最难查。
